# 组合、点评与交易计划需求文档

状态：已 Review（开放问题已决策）  
版本：v0.3
范围：当前 `invest` 项目

## 1. 背景

当前 `invest` 已经具备标的目录、行情、标签自选、交易流水、持仓推导、策略页和 MCP 能力。

当前项目缺少三个连接层：

1. `Strategy` 的用户语义仍然是“策略”，但实际更接近“组合账本”；
2. 分析内容和交易流水之间没有结构化关联；
3. 交易计划没有独立生命周期，无法在策略页集中追踪和复盘。

## 2. 目标

### 2.1 主要目标

1. 将当前 `Strategy` 作为组合账本使用，对外统一称为“组合”。
2. 支持市场、组合、标的三个层级的盘前/盘中/盘后点评。
3. 支持提交、查询、筛选和关联外部资讯，但不由 `invest` 主动抓取资讯。
4. 支持从点评中创建交易计划，并在策略页集中展示。
5. 支持根据行情自动评估计划条件，但不自动下单。
6. 通过 MCP 让 AI Agent 查询、创建、更新和复盘资讯、点评与交易计划。
7. 保留事实数据、主观判断、计划意图和实际交易之间的可追溯关系。

### 2.2 非目标

- 不实现自动交易或自动提交券商订单。
- 不在第一阶段实现任意复杂的脚本化条件表达式。
- 不强制把所有 Obsidian Markdown 迁移成数据库记录。
- 不把外部新闻、行情事实和 AI 判断混成同一种数据。

## 3. 领域术语

### 3.1 组合（Portfolio）

用户实际管理的一组资产和交易账本，例如“银河证券”“华宝证券账户”“代持的父亲账户”。

数据库和现有 API 暂时保留 `Strategy`、`strategy_id` 等兼容名称；页面、MCP 和新文档统一使用“组合”。不新增一个平行的 Portfolio 账本模型。

### 3.2 点评（Commentary）

针对市场、组合或标的，在特定交易日和交易时段形成的分析记录。点评可以包含事实、解释、观点、预判、风险和后续计划。

### 3.3 交易计划（Trade Plan）

对未来交易意图的结构化记录，描述目标标的、所属组合、买卖动作、触发条件、数量/金额、有效期、理由和风险。交易计划不是交易流水。

### 3.4 交易（Trade）

已经发生或被确认记录的买入、卖出、入金、出金。交易是事实，交易计划是意图，两者可以关联但不互相替代。

### 3.5 资讯（Information）

来自外部来源的新闻、公告、研报摘要、宏观数据或市场事件。资讯保留来源和发布时间，主要作为点评和交易计划的事实依据，不等同于 AI 的分析结论。

## 4. 目标数据关系

```text
市场 / 组合 / 标的
          ↓
       点评
          ↓ 产生
      交易计划
          ↓ 条件满足
   待确认信号/提醒
          ↓ 用户确认
        交易
          ↓
    计划执行复盘
```

关系约束：

- 点评可以没有交易计划；
- 一个点评可以产生多个交易计划；
- 一个交易计划可以对应多笔分批交易；
- 一笔交易最多由用户明确关联一个主要交易计划；
- 没有关联计划的交易仍然允许录入；
- 计划触发只产生提醒或待确认状态，不自动产生交易。

## 5. 功能需求

### 5.1 组合管理

当前 `Strategy` 需要补充组合属性：

- 本金；
- 风格：稳健、均衡、激进等；
- 是否自有资产；
- 管理对象/用途；
- 投资方向；
- 约束条件；
- 备注。

现有交易、期初快照、持仓推导和盈亏计算继续复用。UI、MCP 和新接口使用“组合”术语；现有 `/strategies` 接口保留兼容。

### 5.2 点评

点评必须支持以下维度：

- 对象：市场、组合、标的；
- 标的对象使用明确的 `category + symbol`；
- 组合对象使用现有 `strategy_id`；
- 市场对象使用固定或可扩展的市场标识；
- 时段：盘前、盘中、盘后，也允许日度/周度复盘；
- 交易日期和实际创建时间；
- 标题、摘要和结构化正文；
- 正文可以包含段落、标题、列表、指标、事实、观点、风险、预判和引用；
- 输入端可接受结构化 JSON、Markdown 或受限 HTML；
- 存储后以统一结构化格式作为规范数据，页面渲染为友好的 HTML；
- MCP 默认输出 Markdown，也允许请求结构化 JSON；
- 来源：人工、AI、导入、系统生成；
- 原始文件路径或外部引用；
- 引用数据和行情快照；
- 是否包含预判、风险、交易计划。

点评应当支持追加和修订，但不能无痕覆盖历史内容。对事实错误进行修正时，需要保留修订记录或明确的修正关系。数据库不把 HTML 作为唯一规范格式，避免页面展示格式反向限制 MCP 和其他客户端。

规范正文示例：

```json
{
  "version": 1,
  "blocks": [
    {"type": "heading", "level": 2, "text": "基本面"},
    {"type": "paragraph", "text": "营收增速出现改善，但估值仍然偏高。"},
    {"type": "metric", "label": "PE（动态）", "value": 6.14, "unit": "x"},
    {"type": "list", "style": "bullet", "items": ["支撑：ROE 稳定", "风险：息差继续下行"]}
  ]
}
```

页面将 `blocks` 渲染成安全 HTML；MCP 将同一份结构化正文转换成 Markdown。若输入是 Markdown 或受限 HTML，提交时先转换成该规范结构；无法识别的内容保留为 `paragraph`，不丢失原文。

### 5.3 资讯

`invest` 暂时不负责资讯发现、浏览器搜索、抓取和定时采集。外部工具（目前主要是 OpenCLI）完成搜索和初步整理后，通过接口提交资讯。

资讯至少保存：

- 标题、来源名称和原文 URL；
- 发布时间、提交/获取时间；
- 摘要和结构化正文摘录；
- 可选的原文片段格式（纯文本、Markdown 或受限 HTML）；
- 语言和资讯类型；
- 原始搜索上下文或查询词；
- 内容指纹，用于去重；
- 关联对象：市场、行业板块、主题或标的；
- 重要性、可信度。

资讯与对象采用多对多关系。一条资讯可以同时关联某个市场、行业板块和多个标的；同一个标的或市场范围也可以关联多条资讯。组合不作为资讯的直接归属对象，组合点评和交易计划可以引用资讯。

资讯应支持按以下条件筛选：

- 对象：市场、板块、主题、标的；
- 发布时间范围；
- 来源；
- 资讯类型；
- 关键词；
- 重要性；
- 是否已经被点评或交易计划引用。

资讯需要通过 URL、来源、标题和发布时间等信息做幂等去重；重复提交应更新来源元数据，而不是产生多条相同记录。原始 URL 和获取时间必须保留，摘要可被 AI 更新，但不能删除原始来源信息。页面将结构化资讯渲染为 HTML，MCP 默认返回适合 Agent 消费的 Markdown 或结构化 JSON。

资讯和点评的关系：

- 资讯是外部事实或材料；
- 点评是对资讯、行情和组合状态的综合判断；
- 点评可以引用多条资讯；
- 资讯本身不直接产生交易；
- 交易计划应引用点评，必要时同时引用原始资讯。

### 5.4 交易计划

交易计划至少支持：

- 所属组合；
- 目标标的；
- 动作：买入或卖出；
- 数量、金额或仓位比例，三者至少一种；
- 一个或多个触发条件；
- 计划理由；
- 反证和风险；
- 生效时间和失效时间；
- 来源点评；
- 当前状态；
- 关联交易；
- 创建、更新时间和操作者。

第一版条件类型限定为：

- 价格高于某值；
- 价格低于某值；
- 涨跌幅高于/低于某值；
- 突破或跌破均线；
- 突破前高/跌破前低；
- 到达指定日期；
- 人工确认条件。

条件需要保存为结构化数据，同时保留人类可读的描述。第一版不支持任意 Python、SQL 或脚本表达式。

### 5.5 计划生命周期

```text
draft → active → triggered → executed
                 ├→ cancelled
                 └→ expired
```

补充规则：

- `draft` 不参与自动评估；
- `active` 才参与行情条件评估；
- `triggered` 只表示条件满足，不能视为已成交；
- 部分执行需要支持 `partially_executed`；
- 已执行计划仍可复盘，不能删除；
- 过期和取消必须保留原因；
- 同一计划在同一行情事件下不得重复触发。

### 5.6 策略/组合页

组合页使用持仓、交易记录、组合点评、交易计划四个并列 Tab。四个 Tab 都采用一行一条的列表，支持筛选、分页和表头三态排序；第三次点击排序列恢复接口返回的默认顺序。点评列表只展示摘要字段，完整正文通过行点击弹窗查看；交易计划列表直接展示数据，不增加重复标题或说明。

交易计划列表至少包含：

1. 生效中的计划；
2. 已触发、待确认的计划；
3. 即将到期的计划；
4. 最近执行的计划；
5. 已过期/已取消计划；
6. 计划与实际成交的偏差；
7. 计划来源点评和复盘入口。

每个计划应显示：标的、动作、触发条件、当前值、距离触发值、有效期、计划理由、状态和操作入口。

标的显示统一使用名称为主、代码为辅，并可进入对应行情页。组合的初始本金与总资产、净投入等核心指标放在同一区域；投资风格、用途、方向、约束和备注等低频属性从组合列表的 info 入口查看。

### 5.7 标的页和市场页

- 标的页显示该标的的点评时间线和相关交易计划；
- 市场页显示市场级盘前/盘中/盘后点评；
- 组合页显示组合级点评和计划；
- 同一条点评可以被多个页面引用，但正文只有一个来源记录。

### 5.8 MCP / AI Agent

AI Agent 应具备以下能力：

- 查询某个标的、组合或市场的点评；
- 提交资讯及其来源、摘要和标的/市场关联对象；
- 按标的/市场对象、时间、来源、类型和关键词筛选资讯；
- 将资讯关联到点评；
- 按日期、时段、对象和关键词搜索点评；
- 创建点评；
- 追加日志或点评内容；
- 创建交易计划；
- 修改草稿计划；
- 取消、暂停和恢复计划；
- 查询待确认和即将到期计划；
- 评估当前行情是否满足计划条件；
- 将实际交易关联到计划；
- 对已执行计划生成复盘；
- 汇总一段时间内计划的触发率、执行率和结果。

写入交易、确认计划执行、修改历史点评等操作必须要求明确确认。AI 不得因为判断条件满足而自动调用新增交易工具。

## 6. 实施阶段

### 阶段 0：领域确认

步骤：

1. 确认 `Strategy` 对外改称“组合”，内部保持兼容；
2. 确认组合属性和约束字段；
3. 确认点评对象、时段和来源类型；
4. 确认交易计划状态和第一版条件；
5. 输出领域对象和字段决策记录。

验收：需求中的开放问题得到明确结论，并形成领域字段决策记录。

### 阶段 1：组合语义和组合属性

步骤：

1. 给现有策略补充组合属性；
2. 增加组合属性编辑能力；
3. 明确组合期初持仓、现金和交易的录入流程；
4. 通过组合页和 MCP 验证组合账本。

验收：组合可以独立维护交易、期初持仓、现金、约束和点评；现有策略数据保持兼容。

### 阶段 2：点评模型和时间线

步骤：

1. 增加点评存储模型；
2. 支持市场、组合、标的三个对象；
3. 在标的页、组合页、市场页显示时间线；
4. 通过 MCP 查询和搜索点评。

验收：能按对象、日期和盘前/盘中/盘后查看点评。

### 阶段 3：资讯提交、索引和筛选

步骤：

1. 增加资讯和资讯对象关联模型；
2. 提供提交、查询、详情和筛选能力；
3. 实现 URL/标题/发布时间维度的幂等去重；
4. 增加资讯到点评的引用关系；
5. 编写 OpenCLI → AI 整理 → MCP/REST 提交的使用示例；
6. 保留原始 URL、来源和获取时间，不在 `invest` 内实现抓取任务。

验收：OpenCLI 搜索得到的资讯可以提交到 `invest`，按标的/板块/市场和日期筛选，并能从点评回溯原文来源。

### 阶段 4：交易计划基础能力

步骤：

1. 增加交易计划模型和状态流转；
2. 支持第一版结构化条件；
3. 支持从点评创建计划；
4. 在组合页展示生效、待确认和历史计划；
5. 增加创建、修改、取消和查询能力。

验收：AI 或用户可以从一条点评创建计划，计划可以被取消、过期和手动执行，且不会产生自动交易。

### 阶段 5：行情评估与待确认提醒

步骤：

1. 在行情更新任务完成后评估 `active` 计划；
2. 记录评估时间、使用的行情值和命中的条件；
3. 防止同一事件重复触发；
4. 将命中计划显示为待确认；
5. 增加 MCP 查询待确认计划的能力。

验收：条件满足时计划进入 `triggered`，没有用户确认时不写入交易；条件未满足时不改变状态。

### 阶段 6：交易关联和复盘

步骤：

1. 新增交易时允许关联交易计划；
2. 支持一个计划关联多笔分批交易；
3. 记录计划价、实际成交价和执行偏差；
4. 生成计划执行复盘；
5. 支持统计计划触发率、执行率和结果。

验收：能从点评追踪到计划，再追踪到实际交易和最终结果。

### 阶段 7：AI Agent 写入和权限控制

步骤：

1. 增加资讯、点评和计划的追加/写入 MCP 工具；
2. 对交易和计划确认增加显式确认要求；
3. 增加操作审计信息；
4. 增加 Markdown 导出或镜像能力；
5. 为 Claude Code、OpenCode、Codex CLI、pi coding agent 更新接入文档。

验收：AI 可以读取和更新点评/计划，但不能绕过确认直接创建交易；所有写入可追溯。

## 7. 关键问题与决策

以下开放问题已 Review 并形成决策，详见 `docs/portfolio-commentary-trade-plan-decisions.md`。

1. **命名**：页面和 MCP 统一使用“组合”，`Strategy` 仅作为内部兼容名。—— 已决
2. **多计划同标的**：不限制，同一组合可并存多条 active 计划作用于同一标的；触发后分别进入待确认。—— 已决
3. **计划数量**：股数、金额、仓位比例三者都允许，至少一种。—— 已决
4. **触发时机**：默认条件满足即进入待确认；计划可额外声明“需连续 N 日”。—— 已决
5. **条件组合**：支持 AND（全部满足）与 OR（任一满足）两种，默认 AND。—— 已决
6. **时段时区**：第一版只固定 A股窗口（Asia/Shanghai），其他市场暂不区分时段。—— 已决
7. **资讯存储**：摘要为主，可选保存完整正文。—— 已决
8. **资讯关联**：接口层面必须明确指定关联对象，不做“AI 推断待审核”态。—— 已决
9. **计划创建状态**：接口对调用方无感，`draft`/`active` 均可传入，不按来源设限。—— 已决
10. **提醒渠道**：第一版只在页面 + MCP 查询，数据层预留通知钩子。—— 已决

## 8. 决策原则与默认

具体决策见 `docs/portfolio-commentary-trade-plan-decisions.md`。贯穿性原则：

> 接口只承载数据和行为，对调用方（人/AI）无感。安全边界只收敛在两处：① `triggered` 只提醒、绝不自动写交易；② 写交易必须显式确认。其余均为普通数据操作，不为 AI 单独设护栏。

未在决策记录中单独展开的默认取向：

- 点评和交易计划分开建模，点评可以产生计划；
- `invest` 只接收和管理资讯，不主动抓取；OpenCLI 负责发现，AI 负责整理和提交；
- 第一版只支持价格、涨跌幅、均线、前高/前低和日期条件；
- 条件命中只进入 `triggered`，不自动交易；
- 所有历史记录采用追加和修订，不允许无痕覆盖。
