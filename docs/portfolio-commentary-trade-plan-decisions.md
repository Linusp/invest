# 组合、点评与交易计划 —— 领域决策记录

状态：已 Review  
版本：v0.1  
日期：2026-08-25  
范围：`docs/portfolio-commentary-trade-plan-prd.md` 第 7 节开放问题的决策结论

## 贯穿性原则

> **接口只承载数据和行为，对调用方（人还是 AI）无感；安全边界只收敛在两处——① `triggered` 只提醒、绝不自动写交易；② 写交易必须显式确认。** 其余（创建计划、设置 active、关联资讯）都是普通数据操作，不为 AI 单独设护栏。

这条原则统一回答了 #8、#9，也解释了 #2、#4 的取向：系统的职责是**结构化记录意图 + 准确报告条件命中**，最终判断和操作交给用户。

## 决策概览

| # | 问题 | 决策 |
|---|---|---|
| 1 | Strategy 对外命名 | 统一叫「组合」，内部保留 `Strategy`/`strategy_id` 兼容名 |
| 2 | 多计划同标的 | 不限制，同一组合可多 active 计划同标的；触发后分别待确认 |
| 3 | 计划规模表示 | 股数 / 金额 / 仓位比例三者都允许，至少一种 |
| 4 | 触发时机 | 默认条件满足即进待确认；计划可声明"需连续 N 日" |
| 5 | 多条件逻辑 | 支持 AND / OR 两种（默认 AND） |
| 6 | 时段时区 | 第一版只固定 A股窗口（Asia/Shanghai），其他市场暂不区分 |
| 7 | 资讯存储 | 摘要为主，可选存全文 |
| 8 | 资讯关联 | 接口层面必须明确指定，无"AI 推断待审核"态 |

## 逐条决策与理由

### 1. 对外统一称「组合」，内部保留 `Strategy`

- **决策**：页面、MCP、新文档统一使用「组合」；数据库表、字段、现有 API 继续用 `Strategy`/`strategy_id`，不迁移、不破坏现有数据。
- **理由**：`Strategy` 的实际语义是"组合账本"，改对外称呼即可对齐语义；彻底重命名要付出迁移和破坏性改动成本，无实际收益。
- **影响**：不新增平行 Portfolio 模型；UI/MCP 层做术语映射，持久层不变。

### 2. 同一组合允许多计划同标的

- **决策**：不设唯一约束，同一 `(组合, 标的)` 可并存任意多条 active 计划；多条同时命中时分别进入 `triggered`，由用户逐条确认。
- **理由**：阶梯加仓、止盈+止损并存是刚需；既然最终操作是人，冲突不需要系统仲裁，只生成多个待确认项即可。
- **影响**：`(组合, 标的, 状态)` 不加唯一约束；触发冲突退化为"多待确认项"；系统职责收窄为结构化跟踪 + 准确提醒。

### 3. 计划规模三者都允许

- **决策**：股数、金额、仓位比例三种都支持，计划至少填一种。
- **理由**：不同标的和习惯下自然表达方式不同；系统按类型分别校验（股数/金额校验现金或持仓，比例校验组合总资产基准）。
- **影响**：计划模型需三选一或多选的可选字段 + 类型标记；校验逻辑按类型分支。

### 4. 触发时机默认立即，可配置连续 N 日

- **决策**：默认条件满足当日即进入待确认；计划可额外声明"需连续 N 个交易日满足"。
- **理由**：把"多日确认"做成可选条件参数，而非全局规则，兼顾简单与避免假信号。
- **影响**：条件结构需一个可选 `confirm_days`（N≥1）字段；评估时按该字段判定是否需要连续满足。

### 5. 多条件支持 AND / OR

- **决策**：计划条件列表可声明"全部满足"(AND，默认) 或"任一满足"(OR)。
- **理由**：OR 可在一计划内表达阶梯价位（跌破 10 买 / 跌破 9 买），AND 表达多条件共振；两者都常见。
- **影响**：计划条件需一个 `logic` 字段（AND/OR）；评估器按该字段聚合条件命中结果。

### 6. 时段第一版只固定 A股窗口

- **决策**：第一版只实现 A股（Asia/Shanghai）的盘前/盘中/盘后固定边界；其他市场暂不做时段区分。
- **理由**：当前组合（银河/华宝证券）以 A股为主；跨市场时段窗口结构留到后续。
- **影响**：时段枚举先与 A股交易时段绑定；数据模型上时段仍是枚举值，便于后续按市场扩展。

### 7. 资讯摘要为主，可选存全文

- **决策**：默认只存标题、摘要、关键摘录、URL、来源元数据；提交方可选择额外保存全文作为可选附件。
- **理由**：省空间、避版权与失效风险；去重仍靠 URL/标题/发布时间，全文是否存不影响去重。
- **影响**：资讯模型有可选全文字段；默认不抓全文。

### 8. 资讯关联必须明确指定

- **决策**：如果资讯要关联对象，接口层面必须由调用方显式给定标的/市场；也允许提交没有关联对象的通用资讯。不做"AI 推断待审核"中间态，资讯关联只有"已关联/未关联"两种。
- **理由**：接口只负责数据契约，不关心调用方如何得出关联；"待审核关联"是使用层的流程，不该进系统模型。
- **影响**：无"待审核关联"状态与审核流程；关联字段可以为空，但只要提供就必须是明确的对象标识。

### 9. 计划创建状态对调用方无感

- **决策**：接口创建计划时 `draft`/`active` 均为可传状态，不按调用方（人/AI）设限。
- **理由**：与 #8 同原则——接口只承载数据和行为。安全不在"创建计划"这道闸，而在"触发不自动交易"和"写交易需确认"两道闸。
- **影响**：不维护"来源 → 允许状态"的规则；`active` 计划只表示"参与行情评估并提醒"，本身无危险。

### 10. 提醒渠道先页面 + MCP，预留钩子

- **决策**：第一版只在策略页展示 + MCP 查询待确认/即将到期计划，不做 push 通知；数据层预留"待提醒"标记与通知钩子。
- **理由**：先验证"结构化跟踪"本身，避免过早接通知服务；预留钩子保证后续加通知不改模型。
- **影响**：计划/评估模型留通知相关的可选字段或事件标记，第一版不消费。

### 11. 结构化正文，多格式呈现

- **决策**：点评和资讯的规范正文使用结构化 blocks 保存；页面渲染为安全 HTML；MCP 默认转换为 Markdown，也支持返回结构化 JSON。输入可接受结构化 JSON、Markdown 或受限 HTML。
- **理由**：页面需要友好呈现，MCP 需要适合 Agent 消费的文本，同时保留指标、风险、预判和引用等可查询结构。
- **影响**：HTML 不是唯一规范格式；输入格式在写入时归一化，无法识别的内容保留为普通段落，不因渲染方式丢失原文。
